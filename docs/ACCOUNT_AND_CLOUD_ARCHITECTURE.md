# 账号与云端数据架构 V0.1

## 结论

第一版采用 **Supabase Auth + PostgreSQL + Supabase Storage + 现有 FastAPI**：

```text
Expo App
├── 邮箱验证码登录 ───────────────→ Supabase Auth
├── 用户自己的结构化数据 ─────────→ PostgreSQL（RLS 隔离）
├── 私有 PDF 简历 ───────────────→ Storage（私有桶 + 用户目录）
└── 简历解析/面试/报告 + Bearer JWT → FastAPI → DeepSeek
                                      └──────→ 后续持久化与用量记录
```

这不是照搬大型公司的微服务数量，而是采用其适合当前项目的原则：统一用户 ID、默认拒绝、最小权限、业务数据分域、敏感文件私有、不可变快照、审计和可删除。个人开发者暂不维护 Kubernetes、消息总线、数据仓库或多套微服务。

## 身份和密钥边界

| 内容 | 保存位置 | 能否进入 App |
|---|---|---:|
| Supabase Project URL | 客户端环境变量 | 可以 |
| Supabase publishable key | 客户端环境变量 | 可以，但所有表必须启用 RLS |
| 用户 access token | Supabase SDK 管理的本地会话 | 可以 |
| Supabase service-role/secret key | 后端密钥管理 | 绝不可以 |
| DeepSeek API Key | 后端密钥管理 | 绝不可以 |
| 数据库连接串 | 后端密钥管理 | 绝不可以 |

FastAPI 在生产模式下验证 Supabase 签发的 JWT，并从令牌的 `sub` 获取用户 ID。客户端传来的 `user_id` 永远不能作为授权依据。

## 登录方案

- 仅邮箱验证码，不自行保存密码。
- 首次验证码验证成功即创建账号。
- 验证码错误、过期和发送频率限制交给认证服务；界面仍需显示可理解的错误。
- 当前登录邮箱只作账号标识，不复制到业务表。
- 正式发布前需要自定义发信域名、发件人、邮件模板和客服地址。

## 数据域

迁移文件：`supabase/migrations/202609070001_initial_account_cloud.sql`

| 数据表 | 用途 | 删除关系 |
|---|---|---|
| `profiles` | 用户公开设置和账号状态 | 账号删除时级联删除 |
| `user_consents` | 协议、隐私、AI/简历/音频处理授权版本 | 账号删除时级联删除 |
| `resumes` | 简历元数据、确认内容和校验状态 | 账号删除时级联删除 |
| `target_roles` | 用户输入的岗位和 JD | 账号删除时级联删除 |
| `interviews` | 面试生命周期及岗位快照 | 账号删除时级联删除 |
| `interview_questions` | 主问题和追问的顺序、依据 | 面试删除时级联删除 |
| `interview_answers` | 用户确认后的文字回答 | 问题删除时级联删除 |
| `interview_reports` | 报告 JSON、量表版本、模型版本 | 面试删除时级联删除 |
| `ai_usage_events` | Token、耗时、结果，不保存原始提示词 | 账号删除时级联删除 |
| `account_deletion_requests` | 注销任务状态 | 账号删除时级联删除 |
| `audit_events` | 最小化安全审计，不保存简历和回答正文 | 删除用户后只保留去身份记录 |

`interviews` 保存岗位标题和 JD 快照，避免用户修改目标岗位后历史报告失去当时语境。问题、回答和报告分表，避免报告失败时破坏已完成的回答。

## 多层用户隔离

1. 客户端调用 FastAPI 时携带 access token。
2. FastAPI 验证签名、签发方、受众和过期时间，从 `sub` 得到用户身份。
3. 所有业务表都带 `user_id` 并启用 RLS。
4. 跨表外键同时包含 `(资源 id, user_id)`，防止把自己的回答挂到其他用户的面试。
5. PDF 位于私有 `resumes` 桶，路径固定为 `<user_id>/<resume_id>.pdf`。
6. service-role key只允许后端任务使用，不能出现在 Expo 环境变量中。

## 数据生命周期建议（需要产品负责人确认）

下面是建议，不是已经生效的法律承诺：

- 原始语音：当前不上传、不保存；用户明确结束回答后，只提交系统生成的转写文字。若未来上传录音，必须重新设计授权、保留和删除规则。
- 原始 PDF：默认保留以支持重新解析；产品应提供“只删原文件”和“删除整份简历”入口。
- 结构化简历、回答和报告：保留至用户主动删除或注销账号。
- 失败任务的临时文件：建议 24 小时内自动清理。
- 应用日志：禁止写入 API Key、完整简历、完整回答或 access token。
- 注销：用户在 App 内二次确认后提交；后台删除文件、业务数据和认证账号，并记录不含正文的完成状态。

正式上线前必须把保留期限写入真实隐私政策，并让实际代码与政策一致。
